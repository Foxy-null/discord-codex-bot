# Steer後に応答本文が先に出て、後続の出力がない症状の調査

調査日: 2026年10月5日。状態: 原因を確認し、合意した修正を実装した。

## 報告された症状

Codexの実行中に追加入力を送り、Steerした結果が最終出力として先に表示され、その後に何も出力されない。
ユーザーが示した[Discord投稿](https://discord.com/channels/686239106606563425/1556346294153511052/1556559250673893377)から、対象スレッドを特定した。
対象は`Foxy-null/atcoder-devcontainer-template`の作業スレッド`1556346294153511052`、Codex会話`01a107cd-f179-7f81-88e1-f416ad4301c3`。

## 該当ログで確認した原因

同じ作業ターンに2件の最終回答が生成され、Botが後の回答で最終返信の候補を上書きしていた。
元の質問への回答は生成されており、途中出力として送る経路も通っていた。修正前は、作業完了時の返信に追加指示への了承だけが残っていた。

時刻はUTC。Codexの会話ログで確認した順序は次のとおり。

| 時刻         | 内容                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| 06:49:02.013 | 元の質問「Use this templateした人の環境では自動で更新されるの？」                    |
| 06:50:34.301 | 元の質問への最終回答「既存の利用者には自動反映されません」など                       |
| 06:50:34.354 | 追加入力「ログを全部出力するのやめて」が履歴に反映される                             |
| 06:50:39.112 | 追加指示への最終回答「以後、ログ全文は出さず、結果と必要なエラー箇所だけを伝えます」 |
| 06:50:39.140 | 同じ作業ターンの正常終了                                                             |

Botの保存ログでは、両方の回答が`phase: final_answer`、`delivery: null`で、同じターンIDを持つ。
最後に`turn/completed`が`status: completed`で届いている。完了通知待ちや別ターンの追跡漏れは、この事例の説明には当たらない。
指定されたDiscord投稿の時刻は、投稿IDから算出すると06:50:44.833。Discordの投稿本文そのものは直接取得していない。

調査した保存ログは、`2026-10-05T06-50-39-377Z_01a107cd-f179-7f81-88e1-f416ad4301c3.jsonl`。
244行に元の回答、277行に追加指示への了承、280行にターン完了通知がある。

## 確認できたこと

既存の[ADR-0003](adr/0003-running-input-steering.md)は、追加指示の受理通知を送り、作業ターンの完了時に最終返信と後処理を一度だけ行う方針を定めている。

[公式OpenAIドキュメント](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)では、`turn/steer`は実行中のターンに入力を追加し、新しい`turn/started`を発行しない。
`item/completed`は個々の応答などの完了、`turn/completed`は作業ターンの終了を表す。応答の`phase`は`commentary`または`final_answer`を取り得る。

修正前のコードの処理は次のとおり。

1. [Worker.processMessage](../src/worker/worker.ts)は実行中の追加入力を同じターンへ送り、受理通知後に`ok(null)`を返す。追加の入力側の完了処理は呼ばない。
2. `Worker.receive`は`item/completed`の応答本文を途中出力として送る。`phase`が`commentary`でも`delivery`が`async`でもない応答は、最終返信の候補も上書きする。
3. `final_answer`の本文が届いただけではターンを終了しない。同じターンに後続の最終候補が届けば、後続を採用する。
4. `turn/completed`を受けると、`Worker.finishMessage`が途中出力の送信とログ保存を待ち、元の入力の完了処理を一度だけ呼ぶ。処理を終えると、そのターンの通知の追跡を外す。
5. [Discordへの送信](../src/main.ts)は、途中出力では通知を抑制したスレッドへの投稿、最終返信では元の入力への返信を使う。最終返信には取得状況に応じて使用量差分または取得失敗の案内が付く。

原因調査時点で、稼働中のBotの作業場所と、この作業コピーの`src/main.ts`、`src/worker/worker.ts`、`src/worker/codex-executor.ts`は同じ内容だった。

## 実装した修正

同じターンの最終回答を、応答IDをキーにした`Map`で生成順に保持する。
途中応答はその場で届け、ターン完了時の最終返信には元の回答と追加指示への返答を空行で区切って両方含める。
同じ応答IDの通知が重複しても最終返信に本文を重ねず、元の順序を保って内容を更新する。

実装の変更箇所は`src/worker/worker.ts`の回答の型、初期化、保持、ユーザー返信、コミット生成時の読み出しに収まる。
内部のコミット生成は専用の一時会話で行い、最新の回答1件を使う。
ユーザー返信にすべての最終回答を渡すため、元の回答に含まれた添付指定も後の了承で失われず、既存の添付解析を通る。
`turn/completed`で作業終了を判定し、返信と自動コミット・プッシュを一度だけ行う。

## 検証と限界

原因調査時点で、関連するWorker・Codex接続の既存テストは15件成功した。
一時的なFakeクライアントで、Steerの受理だけでは最終返信しないこと、最終候補を先行表示してもターンを終了しないこと、後続の最終候補を採用すること、完了処理後の通知を無視することを確認した。
実モデルで報告された症状を再現したものではない。

該当ログの特定後、異なる応答IDを持つ2件の`final_answer`をSteerの前後に送る最小チェックでも欠落を再現した。
両方の本文は途中出力に届くが、完了時の返信には後者だけが渡った。元の回答と了承の連結を期待するassertionは、修正前のコードで失敗した。

```text
実際: 以後、ログ全文は出しません
期待: 元の依頼への回答\n\n以後、ログ全文は出しません
```

`test/worker.test.ts`に、Steer前後の複数回答、元の回答の添付指定、通知の重複、生成順、完了時の一度だけの返信を確認する回帰テストを追加した。
既存のコミット生成テストでも複数の回答を送り、最後のコミットメッセージだけを採用することを確認した。
修正後のWorker・Codex接続・添付処理の関連テストは19件成功した。
型チェック・lint・formatの確認と全テストも実行し、77件すべて成功した。
最初の調査ではこのBot自身のリポジトリのログを見ており、報告された症状を特定できなかった。
ユーザーが示したURLに対応する別リポジトリの保存ログとCodexの会話ログで、上記のイベント列を確認した。
Botの生ログ保存はターン終了後の通知のみを対象としており、進行中に停止している場合はまだ保存されない。RPCの受理応答やDiscord送信時刻も含まれない。
