# Codex実行中の追加入力の調査と実装案

調査日: 2026年10月5日。調査環境: `codex-cli 0.160.0`。 状態:
調査完了、実装案は未採用。アプリケーションコードは変更していない。

## 結論

今回のエラーは、実行中のCodex会話を別プロセスから再開していることが原因で説明できる。
現在のBotは追加入力を先行処理に渡さず、同じ会話IDで新しい`codex exec resume`を起動する。
そのため、先行プロセスが会話を書き込んでいる間は`already has an active writer`になる。

CLIの実行中の通常送信に合わせるなら、Workerが持続する`codex app-server`接続を所有し、現在の作業ターンへ`turn/steer`で入力を渡す構成を推奨する。
次の依頼を予約するQueueも、同じ接続を使って現在の作業が終わってから入力を送ることで実現できる。
通常送信の既定をSteerにするかQueueにするかは、ユーザーへの確認事項として残している。

## 本来のCodexの動作

| 利用画面・操作    | 実行中の追加入力の扱い                      |
| ----------------- | ------------------------------------------- |
| Codex CLIのEnter  | Steer。現在の作業への補足・修正として渡す   |
| Codex CLIのTab    | Queue。現在の作業終了後の依頼として予約する |
| IDE拡張の通常送信 | 既定はQueue。設定でSteerに変更可能          |

CLIの操作は[公式OpenAIドキュメントのDeveloper commands](https://learn.chatgpt.com/docs/developer-commands)、IDE拡張の既定は[Developer settings](https://learn.chatgpt.com/docs/developer-settings)で確認した。
したがって、「Codexと同じ動作」は一律ではない。今回のように実行中の方向修正を届けたい場合はSteerが対応する。

App
Serverでは、会話を読み込む`thread/resume`、新しい作業を開始する`turn/start`、実行中に入力を追加する`turn/steer`、停止する`turn/interrupt`を使い分ける。
`turn/steer`には現在のターンIDを`expectedTurnId`として渡す。同じターンに入力を追加し、新しいターン開始通知は発生しない。
有効なターンがない場合やIDが一致しない場合は失敗する。モデル・作業場所などのターン設定をSteerで変更することはできない。[公式App Server仕様](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)

Steerの受理は、モデルが既に指示を実行したことを意味しない。停止や再起動とは分けて扱い、Discordには「追加指示を受け付けました」と通知する。
実行済みのファイル変更や外部への操作が巻き戻るという保証もない。
実行中の個々のツールへ指示が反映される正確なタイミングは、この調査では実測していない。

## 現行Botで起きていること

現行コードの経路は次のとおり。

```text
Discord MessageCreate
  → 入力ごとに独立した非同期ハンドラー
  → Admin.routeMessage → MessageRouter.routeMessage
  → 同じWorker.processMessage
  → 新しいcodex exec resume <同じ会話ID>
```

| 根拠                                                                      | 確認した処理と影響                                                 |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| [main.ts](../src/main.ts)、661–662行                                      | 入力ごとに独立して処理を開始する                                   |
| [message-router.ts](../src/admin/message-router.ts)、46–69行              | 同じWorkerへ入力を無条件で渡す                                     |
| [worker.ts](../src/worker/worker.ts)、94–117行                            | 実行中の検査をせず、実行状態・中断用情報・プロセス参照を上書きする |
| [codex-executor.ts](../src/worker/codex-executor.ts)、24–32行             | 呼び出しごとに新規プロセスを起動する                               |
| [worker-configuration.ts](../src/worker/worker-configuration.ts)、18–24行 | 会話IDがあると毎回`exec resume`を選ぶ                              |
| worker.ts、283–286行                                                      | 後続処理の失敗時に、先行処理の停止用情報まで消し得る               |
| worker.ts、579–607行                                                      | 自動コミットのメッセージ生成も同じ会話を別プロセスで再開する       |

追加の影響として、最初の依頼の実行中はまだ会話IDが保存されていないため、追加入力が別のCodex会話を作り、同じ作業コピーを同時に変更し得る。
初回の失敗・中断でも会話IDを保存できない経路がある。

read-onlyの実行でも会話履歴の書き込みは必要なので、コミットメッセージ生成のread-only設定はwriter競合を防がない。
持続するApp Serverへ移行した後に、この別プロセスからの再開を残すと競合が続く。

## 推奨する最小構成

既存のWorkerを、作業スレッドごとの入力とCodex接続の所有者にする。
Workerごとに1つのApp Serverプロセスを必要時に起動し、標準入出力で通信を続ける。
新しいSDKや全スレッド共通の実行基盤は必須ではない。Denoの子プロセスと既存の保存処理を使える。

1. 接続時に`initialize`を送り、応答後に`initialized`を送る。
2. 初回は`thread/start`、保存済みの会話は`thread/resume`で一度読み込む。
3. 会話の読み込み成功直後に、その会話IDを保存する。
4. 待機中の入力は`turn/start`へ渡し、返されたターンIDを保持する。
5. ユーザーの作業ターンが実行中なら、同じ接続で`turn/steer`を送る。
6. ターンの完了通知で状態を確定し、返信と後処理を1回だけ実行する。

会話IDは再起動後の継続用に保存する。ターンIDは現在の実行を識別するために別に管理する。
Discordの作業スレッドIDとCodex会話IDも区別する。

0.160.0の生成型で確認した、実行中の入力例は次の形になる。

```json
{
  "id": 32,
  "method": "turn/steer",
  "params": {
    "threadId": "保存済みのCodex会話ID",
    "expectedTurnId": "実行中のターンID",
    "clientUserMessageId": "DiscordメッセージID",
    "input": [
      {
        "type": "text",
        "text": "追加の指示",
        "text_elements": []
      }
    ]
  }
}
```

`clientUserMessageId`は履歴との照合に使える識別子として扱う。生成型だけでは重複排除を保証できないため、自動再送の根拠にはしない。
画像は既存の保存処理を再利用して`localImage`に変換する。初回入力と追加入力には同じ添付変換を使う。

## 入力が重なる境界の扱い

| Workerの状態                     | 新しい入力の処理                                                   |
| -------------------------------- | ------------------------------------------------------------------ |
| 起動・会話読込・ターン開始の途中 | 順序を保って一時保留し、ターンID確定後に配送する                   |
| 待機中                           | 新しいユーザーターンを開始する                                     |
| ユーザーターン実行中             | Steerを選ぶ場合は現在のターンへ追加する。Queueを選ぶ場合は保留する |
| 停止処理中                       | 停止完了まで新しいターン開始を待つ                                 |
| 自動コミット・プッシュの途中     | 入力を保持し、後処理完了後に次の依頼として渡す                     |
| 接続障害中                       | 入力を保持し、配送状況を確認してから復旧する                       |

入力受付と状態更新だけを短く直列化する。最初の依頼の完了まで受付をロックするとSteerを送れなくなる。
通知を読む処理も継続して動かし、RPCの応答待ちで停止させない。

現状は利用状況の取得や添付ダウンロードを待ってからWorkerへ渡している。
重い添付を含む入力が後から届いた入力に追い越されないよう、Discordで受信した時点で順序を確保する。

Steer送信と先行ターン完了が重なった場合は、拒否された入力を保持する。
「有効なターンなし」やターンID不一致の場合に限り、通知または会話の状態を確認し、後処理を終えてから次のユーザーターンへ渡す。
任意のRPCエラーを新規ターン開始へ置き換えてはいけない。

送信後に接続が切れて応答が不明になった場合は、受理済みかもしれない。
履歴と送信記録を照合するまで無条件に再送しない。
別のBotやCLIが同じ会話のwriterを所有していた場合は、そのプロセスを勝手に停止したりロックを削除したりせず、競合として通知する。

## 返信・停止・自動処理も一緒に直す

**入力受理と作業完了を分ける。**
現在のmain.tsは各入力の処理結果に対して最終返信、添付送信、スレッド改名、自動コミット・プッシュを実行する。
複数のSteer呼び出しに同じ完了結果を返すと、これらが重複する。
Steerは受理結果を返し、作業ターンの完了を扱う処理は1つにする。

**イベント形式を変更する。**
現在の解析は`exec --json`の`type`・`item`を前提にしている。App
Serverの`method`・`params`をそのまま現在の解析へ渡すことはできない。
thread/turn/itemの識別子で通知を振り分け、途中出力を集め、完了状態を基準に最終回答を確定する。
正常終了・失敗・中断を区別し、正常に終了したユーザーターンだけを自動処理の対象にする。

**通常停止はターンを中断する。**
`/stop`は`turn/interrupt`を送り、中断完了を待つ。App
Serverプロセスは次の入力にも使う。
通信不能時やWorker破棄時にはプロセス終了を伴う回復・終了処理が必要になる。
作業スレッドを終了するときは、Codexの終了を待ってから作業コピーを削除する。

**コミット生成をユーザーターンから隔離する。** 同じApp
Server接続に、コミット生成専用のread-only・一時的な会話を作る案を推奨する。
ユーザー会話のwriterと衝突せず、内部プロンプトやread-only設定をユーザー会話へ残さずに済む。
生成結果は内部処理へ返し、ユーザーの追加指示をこの内部ターンへ送らない。
既存のコミット・PR言語指定とリポジトリのコミット規約を生成入力へ引き継ぐ。

`git add`、コミットメッセージ生成、`git commit`、`git push`の全体を後処理として扱う。
その間は次のユーザーターンによるファイル変更を始めない。
途中の失敗ではローカルの変更やコミットを保持する、というADR-0002の方針を維持する。

**持続プロセスの寿命を管理する。**
Worker破棄とBot終了で子プロセスを終了・回収する。
Codexの更新は稼働済みプロセスには反映されないため、実行中の作業を終えた後に接続を作り直す。
現在の「毎回起動するため再起動不要」という更新案内も変更する。

## 実施した確認と実装時の検証

この調査では次を確認した。

- 一時的なFake
  executorで、同じWorkerへ通常入力2件とコミット生成を投入。先行処理を解放する前に、同じ会話への再開が3件始まることをassertionで確認した。
- 以下の既存テストは`26 passed | 0 failed`。同時入力を検証するテストはなく、今回の競合は検出できない。
- インストール済みCLIからTypeScript型を生成し、`turn/steer`と必須の`expectedTurnId`、対応する入力型を確認した。
- 使い捨てのApp Server接続で初期化に成功した。存在しない会話へのSteerは「thread
  not found」と返り、メソッドが受け付けられることを確認した。
- 実行中のユーザー会話を別プロセスで再開する試験や、モデルを使うSteerの動作試験は実施していない。障害当時のCLIバージョンはログからは分からない。

```bash
rtk proxy deno test --allow-read --allow-write --allow-env --allow-net --allow-run test/worker.test.ts test/worker-configuration.test.ts test/codex-stream-processor.test.ts test/message-router.test.ts
rtk proxy codex --version
rtk proxy codex app-server generate-ts --out /tmp/codex-steering-schema
```

実装時には少なくとも、次を検証する必要がある。

1. 同じ作業ターンへの追加入力で、新規プロセスや新規会話を作らずSteerする。
2. 初回の開始途中と完了直前に入力が届いても、入力を欠落・重複させない。
3. 複数のSteerで最終返信、添付送信、自動コミットが重複しない。
4. 停止後も同じ会話で新しい依頼を開始でき、中断を自動コミットの成功と扱わない。
5. コミット生成中のユーザー入力を内部ターンへ渡さず、後処理とファイル変更を競合させない。
6. 異なる作業スレッドは独立して実行できる。
7. 初回失敗・中断でも会話IDを保持し、再接続時には受理不明の入力を無条件再送しない。

## 残る選択

通常のDiscord送信はCLIのEnterに合わせてSteerを推奨する。ユーザーがIDE拡張の既定に合わせたい場合はQueueにする。
Queueを明示的に選ぶUIを追加するかどうかは、別の操作が必要になった段階で決められる。

`exec resume`をスレッドごとに逐次実行するだけでもwriter競合を防ぐことはできるが、追加入力は完了後まで届かない。
これはQueueの実装案であり、Steerを求める場合の解決にはならない。
実行を強制終了してから再開する方式も、現在のターンへ入力を追加する動作とは異なる。
